# MaintainerLint v0.2.0

This file is the release-candidate body for MaintainerLint v0.2.0, intended to become the repository's first tagged GitHub Release after the release PR is merged and the maintainer verifies `main`.

## Highlights

### Conservative brownfield adoption

`maintainerlint init --detect` can inspect high-confidence Python, Node, Rust, and Go repository metadata and propose existing checks without executing package managers, installing dependencies, using an LLM, or accessing the network. Ambiguous and multi-ecosystem repositories fall back to the generic starter instead of guessing.

### Bounded changed-file scope

`maintainerlint scope --strict` lets maintainers encode an explicit changed-file boundary for agent-driven work. Modified, deleted, renamed, or copied paths are checked against declared primary/support patterns, while documentation-impact policy remains an independent gate.

### Human-readable and machine-readable impact evidence

`maintainerlint impact` now renders the same deterministic result model as concise text, PR-friendly Markdown, or the versioned `maintainerlint.impact` JSON schema (`schema_version = 1`). Output format does not change strict exit semantics.

### Cross-platform verification

The repository now runs hosted CI across Linux Python 3.11, 3.12, 3.13 and Windows. Windows-specific path normalization, redaction, CRLF output, and tracked-secret fixtures are covered without adding platform-specific runtime dependencies.

## Existing baseline capabilities

- sequential low-output repository checks;
- sanitized local failure logs;
- deterministic documentation-drift rules;
- high-confidence tracked-secret doctor;
- starter configuration and optional PR template;
- zero third-party runtime dependencies;
- no implicit network calls, telemetry, or LLM API usage.

## Compatibility

- Python: 3.11, 3.12, 3.13;
- configuration schema remains `version = 1`;
- no configuration migration is required from the initial public 0.1.0 code baseline;
- new CLI behavior is additive and opt-in where repository inference is involved.

## Release verification

Before publishing the GitHub Release, the maintainer should confirm the v0.2.0 release PR is merged, the resulting `main` commit is green, and tag `v0.2.0` points to that exact commit. PyPI publication is not part of this release-preparation issue.
